Multi-Model Router

Route every request to the right AI model.

An intelligent routing layer that chooses between local and cloud models by cost, latency, quality and data sensitivity — then shows you the decision and fallback plan.

What this demonstrates

Running every AI request through the most expensive model is how teams end up with an LLM bill nobody can defend. This routes each request between local inference and cloud models based on cost, latency and data sensitivity — showing the routing decision for every call. Hard part: deciding routing policy fast enough that the routing itself does not become the latency problem.

How this is built

Stack. Angular 21 (standalone components, signals, no NgRx) talking to a NestJS API over SSE-over-POST via fetch (EventSource can't send an Authorization header). Postgres holds one append-only request log the dashboard aggregates with SQL (percentile_cont for p50/p95) rather than in JS. Local inference runs on Ollama; OpenAI, Anthropic and Gemini are wired in as optional cloud providers, each marked unavailable — not faked — when its API key isn't configured on this deployment.

The key architectural decision. Routing is a pure function — (prompt, latency budget, provider availability) → decision — with no I/O, so every rule in the policy (sensitive data forces local; complexity sets a capability floor; cheapest adequate model wins, not the best available) is asserted by a unit test rather than only exercised at runtime. Sensitivity detection is regex/keyword, not an LLM call classifying the prompt — asking a model to decide whether to spend a model call is circular, and for privacy it means sending the sensitive text to exactly the place the check exists to protect it from.

Honest trade-off. The regex classifier is fast and auditable but has lower recall than an LLM-based one would — a heuristic can miss PII an actual model might catch. The design leans on the safe side of that asymmetry deliberately: a missed detection sends one prompt to a cloud provider, whereas a false positive only costs some latency by staying local — so sensitivity only ever forces traffic local, never the other way.

About "unavailable" models

This public demo runs with no cloud API keys configured — on purpose, so an unattended demo can't run up a bill. Cloud candidates are marked "provider not configured on this deployment" in the candidate table below; that's expected, not a fault. Every request routes to the local model, and you still see the full decision the router would have made with cloud providers available.

The five routing dimensions

  • Cost — price per million tokens, in or out
  • Latency — how fast a first token is needed
  • Quality — capability floor the prompt requires
  • Capability — context window, reasoning depth
  • Data sensitivity — forces local, never the reverse
